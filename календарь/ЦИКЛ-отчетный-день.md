# Отчётный день — инструкция на один тик

Регламент ОДНОГО прохода. Тик бывает раз в сутки: агент смотрит, не
подошёл ли срок сдачи какого-нибудь отчёта, и не случилось ли вчера
кадрового события, о котором надо сообщить сегодня. В обычный день тик
заканчивается на шаге 2 и молчит.

Сроки — в `КАЛЕНДАРЬ-отчетности.md`. Порядок работы с формами отчётов,
контрольные соотношения и разбор ошибок — скилл `zup-quarterly-reporting`
и `../docs/08-разбор-ошибок-отчетности.md`. Здесь только цикл.

---

## Шаг 0. Клиент тестирования

```
connect_test_client(profileName="AGENT_TEST_CLIENT")
```

## Шаг 1. Вчерашние кадровые события

Это делается КАЖДЫЙ день, до всякого календаря: у подраздела 1.1
ЕФС-1 срок — следующий рабочий день после приказа, и пропустить его
можно ровно один раз.

```
get_table_data(object_type=2, object_name="ПриемНаРаботу",   date_start=<вчера>, date_end=<вчера>)
get_table_data(object_type=2, object_name="Увольнение",       date_start=<вчера>, date_end=<вчера>)
```

Нашлось — **не подавать молча**: порядок работы с
`СведенияОТрудовойДеятельностиРаботниковСЗВ_ТД` в проекте не проверен
ни разу. Доложить человеку: вот документ, вот срок «сегодня», нужно
решение. Записать в `состояние.json` статус `нужно-согласие`.

Ничего не нашлось — молча дальше.

## Шаг 2. Подошёл ли срок

Для каждого отчёта из `настройки.json` (`отчетность.отчеты`) взять срок
из `КАЛЕНДАРЬ-отчетности.md`, перенести вперёд, если он выпал на
выходной, и сравнить с сегодняшним днём:

```
день начала работы = срок − «за-сколько-дней-до-срока»
```

Сегодня раньше — тик закончен, ничего не писать. Сегодня в промежутке
от дня начала до срока — работать. Срок уже прошёл, а в `состояние.json`
статуса `сформировано` нет — работать и пометить `выполнено-с-опозданием`.

**Отчёт делается по закрытому месяцу.** Прежде чем формировать, проверить
по `состояние.json` расчётного цикла и по базе, что все месяцы периода
закрыты: начислена зарплата, проведены ведомости, нет долга по
`АнализЗадолженностиПоЗарплате`. Не закрыты — отчёт не формировать,
сказать человеку, какого месяца не хватает. 6-НДФЛ по недосчитанному
кварталу — это не «черновик», это неверные числа, которые потом придётся
искать по контрольным соотношениям.

## Шаг 3. Не сформирован ли уже

`состояние.json`, ключ вида `6-НДФЛ 3 квартал 2026`. И база:

```
get_table_data(object_type=2, object_name="РегламентированныйОтчет")
```

**Каждое нажатие `ОткрытьФормуОтчета` создаёт НОВЫЙ отчёт, а пометить
его на удаление через MCP нельзя** — ни кнопки в форме, ни в журнале.
Дубли останутся в базе навсегда. Поэтому проверка перед созданием тут
не формальность, а единственная защита.

## Шаг 4. Сформировать

По одному отчёту на организацию, порядком из скилла
`zup-quarterly-reporting`:

```
1. e1cib/app/Отчет.<объект>            ← 6-НДФЛ пишется с ПОДЧЁРКИВАНИЕМ
2. set_value 'Организация' <орг> exact_match:true
3. click_button 'УстановитьПредыдущийПериод'   ← столько раз, сколько надо
4. get_form_element_data 'ПолеВыбораПериодичностиПоказаПериода'  ← ПРОВЕРИТЬ период
5. click_button 'ОткрытьФормуОтчета'
6. click_button 'Заполнить'
7. click_button 'Сохранить'            ← отдельным вызовом
8. click_button 'Проверить'            ← контрольные соотношения
9. click_button 'ПроверитьВыгрузку'
```

Титульный лист заполняется только в момент СОЗДАНИЯ отчёта — ошибку
в реквизитах организации «на лету» не исправить, отчёт придётся
создавать заново. Поэтому реквизиты (ОКТМО, ИНН, ОГРН, регистрационный
номер СФР, ответственные лица) проверяются ДО шага 5, по таблице
из скилла.

## Шаг 5. Прочитать результат проверок

* **Контрольные соотношения.** Нарушений нет — только модальный диалог.
  Есть — открывается окно «Проверка контрольных соотношений» с
  табличным документом `Результат`. Окно само не закрывается и не
  обновляется: перед каждой проверкой закрывать его, а признаком чистоты
  считать его ОТСУТСТВИЕ в `get_window_list_testclient`.
* **Выгрузка.** Всегда модальный диалог; при ошибках — окно «Навигация
  по ошибкам», таблица `ТаблицаСообщений`.

Разбирать удобнее выгрузкой: `save_table_document_to_file('Результат',
format='xlsx')` и `python drafts/инструменты/xlsx2tsv.py`.

## Шаг 6. Не сошлось — не подбирать

Контрольное соотношение не выполняется — это работа на часы, и
методика для неё написана: `../docs/08-разбор-ошибок-отчетности.md`,
таблица рычагов «что на что влияет» в скилле.

**Цикл сам лечит только то, что описано в методике как безопасное.**
Всё остальное — стоп, запись в журнал, вопрос человеку, статус
`частично`. Подгонять число в отчёте, чтобы сошлось соотношение,
нельзя ни при каких обстоятельствах: отчёт сдаётся в налоговую от
имени организации.

## Шаг 7. Отправка — не дело цикла

`отчетность.отправлять` в настройках стоит `false`, и менять это
значение цикл не имеет права. Готовый, проверенный отчёт лежит в базе;
отправляет его человек. Отправленный в ФНС отчёт не отзывается.

## Шаг 8. Записать состояние и доложить

В `состояние.json` — ключ отчёта и периода, статус, дата, срок, по
каждой организации результат проверок, `отправлено: false`.
В `журнал.md` — абзац: какие отчёты сформированы, что показали
контрольные соотношения, что человеку нужно отправить и до какого числа.

В чат — короткий список: отчёт, организация, чисто или нет, срок.
Это тот случай, когда молчать нельзя: человек должен узнать, что
отчётность готова к отправке, ДО срока, а не после.

---

## Границы цикла

* **Формирует и проверяет — не отправляет.**
* **Не закрыт месяц — не формирует отчёт.**
* **Не создаёт дубли**: лишний регламентированный отчёт из базы уже
  не убрать.
* **Не правит данные ради сходимости КС.** Правка документа-источника —
  только по методике и с ведома человека.
* **Подраздел 1.1 ЕФС-1 (приём/увольнение) — только с согласия
  человека**, пока порядок не отработан на живой форме хотя бы раз.
* Тик может идти долго: девять отчётов с проверками — это часы.
  Молчание MCP ошибкой не считать.
