# Как добавить свою операцию

Одна бизнес-операция = один скилл + словари действий по формам, которые
в ней участвуют.

```
.claude/skills/<имя-скилла>/
├── SKILL.md                 ← что спросить у человека, что за чем делать и чего нельзя раньше
└── СловарьДействий.feature  ← что можно сделать с формой: имена полей и кнопок, ловушки
```

Словарь не обязан лежать рядом со скиллом: общие словари по документам
и справочникам живут в `drafts/словари/`, и скилл на них просто ссылается.

Исполняемых сценариев в проекте нет. Почему — в
[архитектуре](02-архитектура.md): маршрут, зашитый в сценарий, встаёт на
первой непредусмотренной мелочи. Порядок действий выбирает модель,
а словарь ограничивает, из чего она выбирает.

## 1. Проверьте, нет ли словаря

Откройте `drafts/словари/ИНДЕКС.md` — там указано, какой файл открывать под
какую задачу. На документы и справочники, названные в руководстве по ЗУП,
словари уже есть (см. [покрытие](09-покрытие-и-проверка-словарей.md)).
Если нужный объект покрыт, переходите сразу к шагу 4.

## 2. Соберите словарь

Источников три, и надёжность у них разная:

| Источник | Чем делается | Насколько верить |
|---|---|---|
| исходники конфигурации | `drafts/инструменты/сгенерировать-словарь.py` | имена настоящие, видимость неизвестна — всегда черновик |
| живая форма | руками через `get_form_analysis`, сверка `сверить-словарь.py` | верить можно |
| прогнанный сценарий | `drafts/инструменты/сценарий-в-словарь.py`, скилл `feature-to-dictionary` | самый надёжный: форма подтвердила каждое имя |

Если у вас уже есть автотест Vanessa на эту операцию и он проходит —
берите третий путь. Если нет — генерируйте из исходников:

```
python drafts/инструменты/сгенерировать-словарь.py --список файл.txt \
    --исходники исходники-конфигурации --вывод drafts/словари
```

Получится файл с тегом `@черновик`. В словаре каждый «Сценарий» — одно
самостоятельное действие («Открыть список», «Создать документ», «Заполнить
организацию»), между собой они порядком не связаны. На файле стоят
`@каталог` и `@НеЗапускать`.

## 3. Проверьте словарь живой формой

Черновик, сгенерированный из `Form.xml`, выглядит для модели точно так же,
как проверенный словарь, и уводит её на элементы, которых на форме не видно.
Поэтому черновик не остаётся в `drafts/словари/`: его либо подтверждают,
либо удаляют.

Откройте форму объекта в клиенте тестирования, снимите состав
(`get_form_analysis(format="gherkin")`) и отдайте сверялке:

```
python drafts/инструменты/сверить-словарь.py \
    --словарь drafts/словари/Должности.feature \
    --живые живые-имена.txt \
    --что "Справочник.Должности, форма нового элемента" \
    --заметка "что выяснилось по существу"
```

Она допишет в словарь блок «ПРОВЕРЕНО ВЖИВУЮ» — какие имена форма
подтвердила, каких не показала, какие показала сверх словаря — и снимет
`@черновик`. Если форма не подтвердила ничего, тег остаётся — такой файл
из `drafts/словари/` удаляют.

Если документ не создаётся («Недоступный пользователю элемент управления
не может выполнять интерактивные действия») — он, скорее всего, закрыт
функциональной опцией. Где такие опции включаются, описано в `CLAUDE.md`,
раздел «Документа нет — включи опцию, а не ищи обход».

Ловушки, найденные на форме, записывайте в тот же словарь комментарием
рядом с действием: значение, которое молча не устанавливается, кнопка,
которая отвечает успехом при отказе 1С, поле, которое появляется только
после выбора другого.

## 4. Напишите SKILL.md

Frontmatter обязателен:

```markdown
---
name: zup-hire-employee
description: Оформляет приём сотрудника на работу в 1С:ЗУП через Vanessa Automation. Используй, когда просят принять, оформить или трудоустроить сотрудника.
---
```

`description` — это то, по чему агент решает, брать скилл или нет. Пишите
там слова, которыми пользователь реально сформулирует задачу.

В теле скилла:

- **что спросить у человека** — входные данные, без которых операцию начинать
  нельзя, и что агент не должен спрашивать, потому что это уже есть в базе;
- **порядок операции** — что за чем и чего нельзя делать раньше. Не шаги
  по кнопкам, а смысл: «кадровые события вводятся до начисления, иначе
  расчёт придётся переделывать»;
- **как понять, что получилось** — проверка по базе (`get_table_data`,
  отчёт), а не по ответу инструмента;
- **что остаётся человеку** — решения, за которые он отвечает перед законом;
- **где смотреть, если чего-то не хватает** — словари, глава руководства.

За образец возьмите `.claude/skills/zup-month-close/SKILL.md`.

Имён элементов формы в скилле быть не должно: они в словаре. Меняется форма
в 1С — правится словарь, меняется порядок работы — правится скилл.

Запись в `.claude/skills/**` агенту запрещена настройками проекта: новый
скилл он может подготовить в `drafts/`, а переносит его человек.

## 5. Добавьте команду для OpenCode

В `.opencode/command/` — короткий файл, который открывает тот же `SKILL.md`.
Инструкции не дублируются, см. [Claude Code и OpenCode](10-claude-и-opencode.md).

## 6. Прогоните от лица человека

Поставьте задачу так, как её поставил бы человек, не читавший ваш скилл,
и посмотрите на две вещи:

- что оказалось в базе — документ проведён, суммы сходятся с отчётом;
- что агент ответил — понятно ли из ответа, какой документ создан, что
  агент решил сам и что стоит перепроверить.

Если агент промахнулся по имени элемента — это находка про словарь или про
форму. Допишите ловушку в словарь, а не обходной путь в скилл.

## Чек-лист

- [ ] На каждую форму операции есть словарь, и на нём нет тега `@черновик`
- [ ] На словаре стоят `@каталог` и `@НеЗапускать`
- [ ] В `SKILL.md` описаны входные данные, порядок и границы операции
- [ ] В `SKILL.md` нет имён элементов формы
- [ ] Признак успеха проверяется по базе, а не по ответу инструмента
- [ ] Операция прогнана на копии базы от начала до конца
- [ ] Есть команда в `.opencode/command/`
- [ ] Feature-файлы сохранены в UTF-8 **with BOM**
