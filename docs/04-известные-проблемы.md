# Известные проблемы

## `get_VanessaAutomation_state` падает с `isCodeEditor`

```
Internal error: Значение не является значением объектного типа (isCodeEditor)
```

Возникает, когда в Vanessa Automation ещё ни разу не открывался редактор
feature-файлов. Лечится открытием любого сценария:

```
mcp__VA__open_feature_file(filePath="<полный путь>/6-НДФЛ.feature")
```

После этого `get_VanessaAutomation_state` отвечает нормально.
Воспроизводится на Vanessa Automation 1.2.043.28.

## `check_syntax` падает с `ЗаписатьЛогВЖРИнформацияСервер`

```
Internal error: Ошибка при вызове метода контекста (ЗаписатьЛогВЖРИнформацияСервер)
```

Та же природа: файл ещё не открывался в редакторе Vanessa. Всегда вызывайте

```
mcp__VA__open_feature_file(filePath=...)
```

перед `check_syntax` — даже если передаёте в `check_syntax` полный путь.
После открытия проверка отрабатывает нормально.
Воспроизводится на Vanessa Automation 1.2.043.28.

## Кракозябры в выводе консоли

Windows-консоль в кодировке 866/1251 покажет UTF-8 кириллицу как `????` или
`Р РµР·`. Это **проблема отображения**, а не файла.

Никогда не «чините» это перекодированием: не пересохраняйте feature-файл,
не переименовывайте файлы, не гоняйте имена через `Encoding.GetString`.
Feature-файлы Vanessa — UTF-8 **with BOM**, и должны такими оставаться.

## Переменная не подставилась в сценарий

Проверьте:

1. `is_global: true` при установке. Локальные переменные Vanessa удаляет
   перед стартом сценария — установленное агентом значение просто пропадёт.
2. Имя переменной в MCP-вызове совпадает с именем внутри `$$...$$` посимвольно.
3. Переменная установлена **до** `run_scenario`, а не после.

## Прочитан результат прошлого запуска

**Устарело с 02.09.2026** — контракт результата убран, переменных
`РезультатВыполненияАгентомШагаN` в сценариях больше нет. Само явление
осталось в другом месте: окно проверки контрольных соотношений тоже
не закрывается само и показывает разбор прошлого отчёта. Закрывайте
окно перед следующей проверкой.

## MCP «не отвечает» на длинном сценарии

Заполнение регламентированного отчёта и расчёт зарплаты идут минутами.
Отсутствие ответа — не ошибка. Не перезапускайте сценарий: получите второй
экземпляр операции в базе. Ждите, потом читайте переменные результата.

## Профиль клиента тестирования не найден

`connect_test_client` требует профиль с именем ровно `AGENT_TEST_CLIENT`.
Имя зашито в `CLAUDE.md` и во всех скиллах. Если у вас профиль называется
иначе — либо переименуйте профиль в Vanessa, либо поменяйте имя во всех
скиллах разом. Половинчатый вариант ломает всё.

## Порт MCP-сервера

В документации Vanessa Automation примеры на портах `9874` и `9876`,
в этом проекте — `8080`. Значение должно совпадать в трёх местах:
параметр запуска `mcpPort`, `.mcp.json`, конфиги в `configs/`.

## `load_features` с путём не обновляет открытый файл

Если файл уже открыт во вкладке редактора Vanessa, то `load_features`
**с путём** и `run_scenario` с `filePath` берут текст из буфера редактора,
а не с диска. Вы правите `.feature`, запускаете — и выполняется старая версия.
Внешне это выглядит как «правка не помогает»: в `get_test_results` просто
нет ваших новых шагов.

Лечится вызовом **без параметров** — он перечитывает текущий файл с диска:

```
mcp__VA__load_features()
```

Проверить, что буфер актуален, можно точечно:
`get_info_about_line_scenario(lineNumber=N)` покажет текст строки так,
как его видит Vanessa. Воспроизводится на Vanessa Automation 1.2.043.28.

## «Все сценарии выполнены успешно» при упавшем шаге

`run_scenario` возвращает `Success` для сценария, у которого шаг внутри
`Попытка` получил статус `Broken`: исключение перехвачено — значит для
Vanessa сценарий отработал штатно.

```
## Результат выполнения сценариев: все сценарии выполнены успешно   <- врёт
```

Это прямое следствие того, что этапы обёрнуты в `Попытка / Исключение`:
мы сами попросили Vanessa не падать. Верить итоговой строке нельзя.
Вердикт берём из двух мест:

1. `get_test_results` — ищем шаги со статусом `Broken`;
2. **база** — документ создан и проведён или нет, отчёт есть в списке
   или нет.

Проверено дважды: на `11_ОтчетностьЕФС1.feature` первый прогон
отрапортовал «успешно», а фактически упал на установке периода;
на сценарии 6-НДФЛ 01.09.2026 — то же самое, «выполнен успешно»
при остановке на середине.

## Клик, открывающий модальное окно, падает как `Broken`

Шаг `И я нажимаю на кнопку с именем 'X'` **выполняет нажатие**, но если в
ответ 1С открывает модальное (блокирующее) окно, шаг не может вернуть
управление и через ~6 секунд получает статус `Broken`.

Воспроизводится на записи нового сотрудника: 1С показывает диалог
«Найден похожий человек».

Лечится не борьбой, а ожиданием: клик выносится в отдельный блок
`Попытка / Исключение`, который **не останавливает** сценарий, а следующий
блок разбирает диалог.

```gherkin
	*нажмём записать и закрыть
		Попытка
			И я нажимаю на кнопку с именем 'КомандаЗаписатьИЗакрыть'
		Исключение
			# сюда попадаем, когда 1С прервала запись вопросом
	*ответим на вопрос о похожем человеке
		Попытка
			Если появилось окно с заголовком "Найден похожий человек" Тогда
				И я нажимаю на кнопку с именем 'ДаЭтоТотКтоМнеНужен'
				И я нажимаю на кнопку с именем 'КомандаЗаписатьИЗакрыть'
			Тогда открылось окно "Сотрудники"
```

Оба исхода — с диалогом и без — приводят к одному состоянию. Честность
держится на проверке `Тогда открылось окно "Сотрудники"` в следующем
блоке: если запись не прошла, упадёт именно она.

## `run_scenario` с `mode: all` запускает **все** загруженные фичи

`mode: all` — это «все сценарии загруженных feature файлов», а не «все
сценарии указанного файла». Если в дереве Vanessa лежит несколько фич,
`run_scenario(filePath="12_...", mode="all")` прогонит и `12`, и `13`,
а `get_test_results` вернёт результат только одной из них.

Итог выглядит загадочно: переменные результата содержат тексты из чужого
сценария. Для одиночного запуска:

```
open_feature_file(filePath=...)
load_features()                      # без параметров, перечитать с диска
run_scenario(mode="reloadAndRun")
```

## Гонка на только что открытой форме

Ввод в поля формы сразу после её открытия может «пройти» вхолостую: шаг
получает `Success`, но значение не установилось. Признак в
`get_test_results` — подозрительно быстрый шаг: выбор из выпадающего
списка за `1 мс` вместо обычных `~100 мс`. Следующие шаги падают.

Не лечится паузой — лечится проверкой. После группы полей ставьте
`Тогда элемент формы с именем '...' стал равен "..."`: этот шаг ждёт
появления значения и заодно документирует ожидание.

```gherkin
	И из выпадающего списка с именем 'ФизлицоПол' я выбираю точное значение "$$ПеременнаяПол$$"
	Тогда элемент формы с именем 'ФИО' стал равен "$$ПеременнаяФИО$$"
	И элемент формы с именем 'ФизлицоПол' стал равен "$$ПеременнаяПол$$"
```

## `execute_feature_step` зависает на шаге выбора файла

`execute_feature_step` на строке `И я выбираю файл '...'` не возвращает
управление — шаг уходит в бесконечное ожидание, вызов приходится снимать.
Отлаживайте такие шаги только полным прогоном сценария.
Воспроизводится на Vanessa Automation 1.2.043.28.

## Промо-окно 1С-Отчетности «Сдавайте отчетность прямо из программы»

Форма `Обработка.ОбщиеОбъектыРеглОтчетности.Форма.ПредложениеОформитьЗаявлениеНаПодключение`
вклинивается между «Заполнить» и «Сохранить» и забирает фокус.

Показ управляется двумя значениями в хранилище общих настроек — видно в
модуле самой формы:

```bsl
БольшеНеПоказывать = ХранилищеОбщихНастроек.Загрузить(
	"Обработка.ОбщиеОбъектыРеглОтчетности",
	"НеПоказыватьПредложениеОформитьЗаявлениеНаПодключение");
ВремяПоследнегоНапоминания = ХранилищеОбщихНастроек.Загрузить(
	"Обработка.ОбщиеОбъектыРеглОтчетности", "ВремяПоследнегоНапоминания");
```

После первого показа окно молчит **4 часа**. Поэтому сценарий, отлаженный
днём, падает на следующее утро — худший вид нестабильности.

Три способа, от надёжного к простому:

1. Один раз поставить флаг для пользователя, под которым работает клиент
   тестирования: `НеПоказыватьПредложениеОформитьЗаявлениеНаПодключение = Истина`.
   Из сценария — шагом `И я выполняю код встроенного языка на сервере
   через буфер обмена (Расширение)`, требуется расширение VAExtension.
2. Дождаться появления окна вручную и отметить в нём «Больше не показывать»
   — это тот же флаг, только через интерфейс.
3. Держать в сценарии условие на случай чужой базы, где флаг не ставили:

```gherkin
	Если появилось окно с заголовком "Сдавайте отчетность прямо из программы" Тогда
		И я закрываю окно "Сдавайте отчетность прямо из программы"
		И я активизирую окно "ЕФС-1*"
```

Пункт 3 нужен всегда: он ничего не стоит, когда окна нет.

## `execute_feature_step` не возвращает управление

Наблюдалось 25.08.2026 на Vanessa Automation 1.2.043.28: вызов виснет и не
отвечает ни через две минуты, ни позже. Воспроизвелось трижды подряд, в том
числе на безобидных шагах:

```
Дано Я открываю основную форму документа "ВедомостьНаВыплатуЗарплатыВКассу"
И я закрываю все окна клиентского приложения
```

При этом всё остальное работает: клиент тестирования подключён,
`get_window_list_testclient` отвечает, скриншот снимается, модальных окон на
экране нет, `open_feature_file`, `load_features` и `check_syntax` отрабатывают
за секунду. Форма после зависшего вызова так и не открывается.

Причина не найдена. Но разведку формы можно сделать в обход шагов — прямыми
инструментами MCP:

```
window_management(action="open_navigation",
                  navigation_link="e1cib/list/Документ.<ИмяДокумента>")
manage_form_elements(action="click_button", element_name="ФормаСоздать")
get_form_analysis(format="elements")
```

Так снимается дерево элементов новой формы вместе с фактической видимостью
каждого поля — то, ради чего обычно и открывают форму. Закрыть за собой:

```
window_management(action="close", window_title="<Заголовок окна>")
```

Этим способом сняты формы трёх ведомостей на выплату.

## Отбор по организации в списке документов молча не устанавливается

Список `НачислениеЗарплаты` имеет поле отбора с генерируемым именем
`КомпоновщикНастроекПользовательскиеНастройкиЭлемент4Значение`.

Ни `из выпадающего списка ... я выбираю точное значение`, ни
`в поле ... я ввожу текст` в него не попадают. Шаги возвращают **Success**,
поле остаётся пустым, а флаг использования отбора при этом включается.

Дальше происходит худшее: список с отбором «организация = пустая ссылка»
становится пустым, и любой поиск по нему отвечает «ничего не найдено».
Сценарий проверки при этом рапортует успех. Это ложноотрицательный ответ —
агент скажет человеку «документов нет» там, где они есть.

Даже страховка `Тогда элемент формы с именем '...' стал равен "..."` здесь
не спасает: она тоже отработала Success на пустом поле. Проверено
25.08.2026 скриншотом формы после прогона.

**Лечение — не устанавливать отбор вообще.** Организация проверяется прямо
в поиске строки, второй колонкой:

```gherkin
	И я снимаю флаг с именем 'КомпоновщикНастроекПользовательскиеНастройкиЭлемент4Использование'
	И в таблице "Список" я перехожу к строке
		| 'Месяц начисления'              | 'Организация'                           |
		| '$$ПеременнаяМесяцНачисления$$' | '$$ПеременнаяНаименованиеОрганизации$$' |
```

В таблице Gherkin для этого шага работают **заголовки** колонок
(«Месяц начисления», «Организация»), а не имена элементов.

Проверено в обе стороны: `Январь 2013` находит документ № 0000-000002
от 31.01.2013, `Январь 2026` честно отвечает «не найдено». Обратный тест
здесь обязателен — без него отличить «нет документа» от «поиск сломан»
невозможно.

## Переменные результата пишутся в локальный контекст, а читаются без `is_global`

**Устарело с 02.09.2026: контракт результата убран, и эта запись —
причина, по которой его убрали.** Оставлена как история; последний
абзац про входные переменные по-прежнему в силе.

Сценарий писал `РезультатВыполненияАгентомШагаN` шагом
`Я запоминаю значение выражения ... в переменную`. Это **локальный**
контекст Vanessa, а не глобальный.

Читать результат надо без флага:

```
manage_variables(action="get", name="РезультатВыполненияАгентомШага3")
```

С `is_global=true` вернётся **другая** переменная с тем же именем — та,
которую агент сам создал при очистке перед запуском. Выглядит это как
«сценарий ничего не записал»: значение пустое, хотя прогон прошёл.
Проверено 25.08.2026.

Входные переменные, наоборот, устанавливаются с `is_global=true` — иначе
Vanessa удалит их перед стартом сценария. То есть у входа и у результата
разные области видимости, и это надо держать в голове.

## `set_value` по подстроке подставляет не то значение

При прямом исполнении через `manage_form_elements` вызов

```
manage_form_elements(action="set_value", element_name="СпособВыплаты", value="Аванс")
```

доложил «Значение 'Аванс' было успешно установлено», а в поле оказалось
**«Вознаграждение сотрудникам по договорам ГПХ»**. По умолчанию `set_value`
ищет по подстроке и берёт первое подходящее значение списка.

Для ведомости на выплату это означало бы, что вместо аванса в документ
попадут вознаграждения по договорам ГПХ — другие люди и другие суммы.
Поймано только проверкой `get_form_element_data` сразу после установки.
Проверено 25.08.2026.

**Лечение:** для полей выбора всегда передавать `exact_match: true`.
С ним значение встало правильно.

Обобщение, которое стоит держать в голове при прямом исполнении:

| Вид поля | Чем ставить |
|---|---|
| поле выбора (организация, способ выплаты) | `set_value` с `exact_match: true` |
| строковое поле (месяц строкой) | `input_text` |
| поле даты | `input_text`, иногда после `activate_header_element` |

`set_value` на поле даты падает с «не получилось выбрать из списка выбора»:
он принимает дату за список. А `input_text` на дате в форме ведомости
сначала отказал с «Неподходящий тип элемента управления» и заработал только
после `activate_header_element` по тому же полю. На форме начисления аванса
то же самое поле принимает `input_text` сразу — поведение зависит от формы.

**Вывод, который дороже самих рецептов:** проверка значения после каждой
установки — не перестраховка. За один прогон она поймала две подмены,
каждая из которых прошла бы как «успешно выполнено».

**Дополнение 30.08.2026.** Третий случай той же подмены: выбор вида
документа, удостоверяющего личность. Запрос «Паспорт гражданина
Российской Федерации» — название, которого в справочнике нет, там
«Паспорт гражданина РФ» — доложил об успехе и поставил **«Временное
удостоверение взамен удостоверения гражданина, подлежащего призыву на
военную службу»**, первый элемент списка. Приём на работу с таким видом
документа провёлся бы молча и испортил бы ЕФС-1.

Заодно выяснилось, что `exact_match: true` полезен не только
правильностью: при неточном имени он выдаёт ошибку **со списком всех
допустимых значений поля**. Это самый дешёвый способ узнать, как
значение называется на самом деле, — дешевле открытия формы выбора.

## Ведомость на зарплату подхватывает задолженность прошлых лет

Ведомость со способом выплаты «Зарплата за месяц» заполняется так, чтобы
погасить **всю** незакрытую задолженность перед сотрудниками, а не только
за указанный месяц. Это штатное поведение, описанное в руководстве
(раздел 16.3.2): учитываются все зарегистрированные суммы по месяц выплаты
включительно, включая незакрытые взаиморасчёты прошлых периодов.

На демонстрационной базе это выстреливает сразу. 25.08.2026 ведомость на
зарплату за январь 2026 по Крон-Ц дала Булатову 113 970,00 при январском
авансе 17 400,00, и в расшифровке колонки «К выплате» стояло
**«в т.ч. за сентябрь 2021»**: база тянет невыплаченные долги с 2021 года.

Для агента это ловушка: человек говорит «выплати зарплату за январь», а
ведомость молча собирается выплатить всё за четыре года. Ни ошибки, ни
предупреждения 1С при этом нет.

**Что делать.** После заполнения ведомости на зарплату смотреть расшифровку
колонки «К выплате» хотя бы по одной строке. Если там появляются чужие
месяцы — остановиться и сказать человеку, а не проводить. Сумма ведомости,
сильно превышающая «начислено минус удержано» за месяц, — тот же признак.

Отдельно: ведомость аванса этой проблемы не имеет. Аванс заполняется по
способам выплаты аванса за конкретный месяц, и сумма сошлась с документом
начисления копейка в копейку.

## Список регистра накопления вешает MCP-сервер

`window_management(open_navigation, "e1cib/list/РегистрНакопления.<Имя>")`
открывается нормально, но следующий же `get_form_analysis` не возвращает
управление: вызов уходит в фон по 120 секунд, и вместе с ним встаёт весь
MCP-сервер — соседние вызовы тоже начинают висеть. Помогает `TaskStop`
плюс ожидание: сервер отвечает не сразу.

Причина, по-видимому, в размере динамического списка: в регистре
«Расчеты налогоплательщиков с бюджетом по НДФЛ» десятки тысяч записей,
и VA пытается собрать их все в gherkin-представление.

**Что делать.** Регистры читать не списком, а **Универсальным отчётом**:
`e1cib/app/Отчет.УниверсальныйОтчет` → Тип объекта → Имя объекта →
Имя таблицы = «Остатки и обороты» → `СформироватьОтчет` →
`save_table_document_to_file('ОтчетТабличныйДокумент', format='xlsx')`.
Рецепт целиком — `drafts/словари/УниверсальныйОтчетКакОкноВРегистры.feature`.

## Индексы полей быстрых настроек отчёта съезжают

В Универсальном отчёте поля называются
`КомпоновщикНастроекПользовательскиеНастройкиЭлемент0Значение`,
`…Элемент1Значение` и так далее — по порядку на форме, а не по смыслу.
Как только выбран периодический объект, появляется поле периода, и все
индексы сдвигаются на единицу. У непериодического регистра сведений
периода нет — и они сдвигаются обратно.

Из-за этого одна и та же строка кода то попадает в «Имя объекта»,
то в «Тип объекта». Ошибка при этом внятная: инструмент печатает
заголовок поля и список допустимых значений — по ним сразу видно,
куда попал.

**Что делать.** После каждой смены объекта перечитывать форму
`get_form_analysis(format="gherkin")`, а не запоминать индексы.

## Конвертер xlsx выбрасывал пустые ячейки

`scratchpad/xlsx2txt.py` печатал только непустые ячейки, соединяя их
через ` | `. На отчётах, где часть колонок пустая (а в выгрузке регистра
пустая половина), колонки съезжают, и разбор по индексу даёт
**правдоподобный мусор**: 30.08.2026 из-за этого дважды получилось
«недоудержано 2 369 704» вместо настоящих 19 529, и обе цифры выглядели
одинаково правдоподобно.

Это худший вид ошибки: не падение, а тихий неверный ответ.

**Что делать.** Для любых выгрузок с возможными пустыми ячейками
использовать `drafts/инструменты/xlsx2tsv.py` — он сохраняет номера
колонок и пишет TSV фиксированной ширины. Старый конвертер оставлен
только для коротких отчётов вида «параметр — значение».

## Окно проверки контрольных соотношений показывает прошлый результат

Кнопка `Проверить` в регламентированном отчёте ведёт себя по-разному:
если нарушения есть — открывается окно «Проверка контрольных соотношений»,
если нет — показывается модальный диалог «При проверке контрольных
соотношений ошибки не обнаружены».

Окно при этом **само не закрывается и не обновляется**. Проверив один
отчёт с ошибками, а потом другой без них, легко прочитать в окне старый
результат и решить, что ничего не изменилось. Ровно это и произошло
30.08.2026 при переходе от Крон-Ц к филиалу.

**Что делать.** Перед каждой проверкой закрывать окно
`window_management(close, "Проверка контрольных соотношений")`, а
признаком чистоты считать ОТСУТСТВИЕ этого окна в
`get_window_list_testclient` после нажатия `Проверить`.

## Поле «…Строкой» молча принимает не то значение

`НДФЛИсчисленныйПоСтавке13МесяцНалоговогоПериодаСтрокой` на ввод
«Март 2026» отвечает успехом, документ проводится — а в реквизите
оказывается текущий месяц сеанса (31.08.2026). Отчёт после этого молча
не меняется, и выглядит это как «правка не сработала».

Такие поля — строковое представление даты. Вводить в них ДАТУ:
`31.03.2026`.

**Что делать.** Это частный случай правила 4а из `CLAUDE.md`: после
записи документа проверять реквизит через `get_object_attributes`
(`data_mode="single_tabular_section"` для табличной части), а не верить
успешному ответу инструмента.

## Ведомость замораживает аналитику НДФЛ и не обновляет её

У ведомости есть табличная часть **НДФЛ** (на форме не видна, читается
`get_object_attributes(tabular_section_name="НДФЛ")`). В ней по строке на
каждый документ-основание, и реквизит `МесяцНалоговогоПериода` — это на
самом деле **дата получения дохода**. Именно она уходит в аналитику
движения регистра «Расчеты налогоплательщиков с бюджетом по НДФЛ».

Значение фиксируется в момент заполнения и дальше не пересчитывается.
Если поправить документ-основание (например, дату выдачи подарка),
ведомость останется со старой датой. Не помогают ни повторное
проведение, ни кнопка «Обновить налог» — она подтягивает только новые
суммы.

**Что делать.** `Отменить проведение` → `Заполнить` → `Провести`.
И сразу проверять состав: у ведомости с видом выплаты **«Аванс»**
`Заполнить` очищает состав в ноль и не выдаёт ни одного сообщения.
Откат — `Перечитать` → «Да» → `Провести`.

## Контекст `Я запускаю сценарий открытия TestClient` перезапускает клиент

Строка, которая стоит в шапке почти каждого feature-файла проекта:

```gherkin
Контекст:
	Дано Я запускаю сценарий открытия TestClient или подключаю уже существующий
```

в разовом сценарии под живую форму делает не то, что обещает названием.
30.08.2026 при запуске такого сценария клиент тестирования **поднялся
заново**: закрылись все 25 открытых окон (отчёты, документы, регламентные
отчёты) и пропало незаписанное исходящее письмо, которое готовилось
до этого. Данные не пострадали — потерялось только несохранённое.

**Что делать.** В сценариях, которые пишутся под уже открытую форму,
блок `Контекст:` не писать вовсе: клиент уже подключён через
`connect_test_client`, и сценарию ничего поднимать не нужно.
Если форма готовится долго — записать её (`Записать`) до первого
`run_scenario`, а не после.

## Ввести многострочный текст в поле можно только шагом из файла

`manage_form_elements(action="input_text")` кладёт в поле одну строку:
переносы теряются. Для писем, комментариев и описаний это заметно сразу.

Рабочий способ — шаг Vanessa:

```gherkin
	И в поле с именем 'ТекстПисьма' я ввожу текст из файла "C:\...\telo.txt"
```

Он ставит текст целиком, с абзацами, но **заменяет содержимое поля
полностью** — всё, что там было (например, автоматически подставленная
цитата исходного письма), пропадёт. Нужна цитата — класть её в тот же файл.

Запускать только полным прогоном (`open_feature_file` → `load_features` →
`run_scenario`): через `execute_feature_step` этот шаг виснет так же,
как шаг выбора файла, — 300 секунд молчания и обрыв вызова по таймауту.

## Диалог выбора файла: единственный рабочий приём

Кнопки вида «Добавить вложение…» открывают модальный диалог ОС, который
MCP водить не умеет: клиент тестирования встанет, пока диалог не закроет
человек. В Vanessa есть ровно два шага про этот диалог — «Я выбираю файл»
и «Я отменяю выбор файла», оба подкладывают результат **заранее**.

Порядок, который работает (проверено на вложениях письма 30.08.2026):

```gherkin
	И я выбираю файл "C:\...\отчет.xlsx"
	И я нажимаю на кнопку с именем 'ДобавитьВложениеКоманда'
```

Диалог при этом вообще не появляется. Один такой блок — одно вложение;
на три файла нужны три пары шагов. Сама кнопка нажимается только внутри
сценария: нажать её инструментом MCP и «подложить» файл потом нельзя.

## Кнопка «Отправить» на письме не отправляет письмо

Классическое молчаливое несрабатывание. На форме исходящего письма
нажатие `Отправить` закрывает окно — и это выглядит как успех.
На самом деле письмо только переходит в статус **«Исходящее»**,
то есть встаёт в очередь: `ДатаОтправления` пустая,
`ИдентификаторСообщения` пустой, ни одного сообщения об ошибке.

Реально письмо уходит командой **«Отправить и получить»**
(`СписокОтправитьПолучитьПочту`) в журнале «Взаимодействия»
(`e1cib/command/ЖурналДокументов.Взаимодействия.ОткрытьСписок`).
Она же забирает новую входящую почту.

Вторая ловушка сверху: в журнале при варианте навигации «По предметам»
эта кнопка **есть в дереве элементов, но невидима**, и нажатие падает
с «Невидимый пользователю элемент управления не может выполнять
интерактивные действия». Сначала `УстановитьВариантНавигацииПоПапкам`,
потом жать. Видимость проверять через `get_form_element_data`,
а не по дереву элементов.

**Как убедиться, что письмо ушло** — `get_table_data(object_type=6,
navigationLink=…)`: `СтатусПисьма` = «Отправлено», `ДатаОтправления`
заполнена, `ИдентификаторСообщения` выдан SMTP-сервером.

## Выбор из формы списка молча не срабатывает, если выделены все строки

Документ «Изменение штатного расписания», кнопка «Изменить позицию»
открывает форму выбора «Штатное расписание». Дальше:

```
navigate_to_row(table_name="Список", row_criteria="Подразделение=…;Должность=Эксперт")
click_button("ФормаВыбрать")
```

Оба вызова отчитались об успехе. Окно выбора осталось открытым, таблица
`Позиции` документа осталась **пустой**. Ни ошибки, ни сообщения.
Повтор через `select_row` — тот же результат. Три попытки подряд.

Причина нашлась в диагностике соседнего вызова: «Количество выделенных
строк в таблице: **34**». Форма выбора открывается с выделенными ВСЕМИ
строками; `navigate_to_row` переводит текущую строку, но выделение не
трогает, и выбор в этом состоянии не проходит.

**Лечение:** перед выбором активизировать любую колонку — это схлопывает
выделение до текущей строки.

```
activate_column(table_name="Список", value="Наименование")
navigate_to_row(table_name="Список", row_criteria="…")
select_row(table_name="Список")
```

После этого строка появилась в документе с первого раза.

**Проверять результат нужно по таблице документа-приёмника**, а не по
тому, закрылось ли окно выбора: форма выбора позиций остаётся открытой
и после удачного выбора.

Побочно: `select_row` в таблице формы документа работает как **двойной
клик**, а не как «выделить строку». В таблице `Позиции` он открывает
форму позиции — именно там и правится количество ставок.

## `navigate_to_row` и `activate_column` требуют разного

Два действия одного инструмента `manage_form_elements`, одна и та же
таблица, разные ключи:

| Действие | Что передавать | Пример |
|---|---|---|
| `navigate_to_row` | **заголовок** колонки | `Подразделение=…` |
| `activate_column` | **имя** поля | `ПозицииКоличествоСтавок` |

Мало того, `navigate_to_row` строит из критериев структуру, поэтому
заголовок обязан быть допустимым именем переменной. Колонка «Наименование
позиции» (два слова) даёт

```
Ошибка при вызове метода контекста (Вставить):
Задано неправильное имя атрибута структуры
```

хотя сам инструмент только что перечислил её среди допустимых. Отбираться
по такой колонке нельзя — брать однословную («Подразделение», «Должность»,
«Код»). Отбор по двум колонкам через `;` работает и заменяет отбор по
длинному наименованию.

Обратная сторона той же медали: `activate_column` по заголовку
«Наименование позиции» падает с «поле не найдено», нужно имя
`Наименование`.

**Полезно:** оба действия при ошибке печатают **полный список колонок
с именами И заголовками**. Это самый быстрый способ узнать и то, и
другое — быстрее, чем `get_form_analysis` по большой форме.

## Ошибка `get_table_data` оставляет висеть служебное окно

`get_table_data` по справочнику `КлассификаторЗанятий` (ОКЗ, несколько
тысяч элементов, иерархический) стабильно падает:

```
Internal error: Ошибка при вызове метода контекста (ПрочитатьJSON)
```

Само по себе это терпимо — справочник читается через форму. Хуже
побочный эффект: после каждой такой ошибки в клиенте тестирования
остаётся открытым служебное окно **«VAExtension получение данных из
базы»**, и оно перехватывает фокус. Следующая команда приходит не в ту
форму: `window_management activate` по нужному окну возвращает заголовок
служебного, а `click_button` падает с «Элемента формы с именем … не
найдено» и списком чужих кнопок (`ФормаВыполнитьОбработку`,
`ФормаПолучитьПараметры`).

**Лечение:** после неудачного `get_table_data` закрывать окно явно —
`window_management(action="close", window_title="VAExtension*")` — и
только потом продолжать.

Диагностический признак: в ответе на любое действие вдруг появился
элемент `ОтборПоНаименованию` или `КоличествоСсылок` — вы работаете
со служебной формой расширения, а не со своей.

## Две кнопки с одинаковым заголовком, работает не первая

На форме документа «Прием на работу» есть `ФормаПровести` и
`КомандаПровести`, обе с заголовком «Провести». Первая — **невидима**:

```
Ошибка при вызове метода контекста (Нажать): Невидимый пользователю
элемент управления не может выполнять интерактивные действия.
```

То же самое с парами `ФормаЗаписать` / `КомандаЗаписать` и
`ФормаПровестиИЗакрыть` / `КомандаПровестиИЗакрыть`. При этом на форме
«Изменение штатного расписания» рабочей оказывается ровно наоборот
`ФормаПровести` — то есть по имени угадать нельзя, это свойство
конкретной формы.

**Лечение:** `get_form_analysis(format="buttons")` и брать ту, у которой
`Видимость:Да`. Словарь, снятый с исходников, обе кнопки перечисляет как
равноправные — по Form.xml различить их невозможно.

## Картинки в письме есть, а «вложений нет»

Входящее письмо размером 5,5 МБ при тексте в 250 знаков, реквизит
`ЕстьВложения` = **нет**, таблица `Вложения` на форме имеет
`Видимость:Нет`. Три скана документов при этом в письме есть: отправитель
вставил их в тело, и они пришли inline-частями, на которые в `ТекстHTML`
ссылаются `<img src="cid:…">`.

Через форму до них не добраться никак: таблица вложений невидима, потому
что по мнению 1С вложений нет.

**Лечение** — вытащить письмо целиком и разобрать снаружи:

```
И я выбираю файл "…\zadanie.eml"
И я нажимаю на кнопку с именем 'ФормаЖурналДокументовВзаимодействияСохранитьПисьмоНаДиск'
```

путь с именем файла ставится ДО нажатия кнопки, каталог должен
существовать. Дальше обычный `email.message_from_binary_file` с
`policy=policy.default`, обход `msg.walk()` и отбор частей по
`content_type().startswith("image/")`. Имена файлов сохраняются
(«паспорт.png»), содержимое берётся `part.get_payload(decode=True)`.

**Признак, по которому это опознаётся заранее:** несоответствие между
`Размер` письма и длиной `Текст`, плюс `cid:` в `ТекстHTML`.

## `save_table_document_to_file` рапортует успех в несуществующий каталог

Сохранение печатной формы в путь, где каталога ещё нет:

```
save_table_document_to_file(file_name="…\uvolnenie\01-prikaz-T8.pdf",
                            form_element_name="ПечатнаяФорма1", format="pdf")
```

вернуло `# Табличный документ ПечатнаяФорма1 сохранен`. Файла при этом
нет, а в клиенте тестирования повис модальный диалог:

```
Каталог не обнаружен '…\uvolnenie\01-prikaz-T8.pdf'.
3(0x00000003): Системе не удается найти указанный путь.
```

Обнаружился он только на следующем действии, которое упало с посторонней
ошибкой («Невозможно перейти к следующей строке»), а в тексте ответа
пришёл текст диалога. То есть ошибка всплывает не там, где случилась.

**Лечение:** создавать каталог заранее (`mkdir -p`) и после сохранения
проверять файл на диске — `ls`, а не доверять ответу инструмента.
Диалог закрывается нажатием кнопки `OK`.

## Из комплекта печатных форм доступна только текущая

`ОбщаяФорма.ПечатьДокументов` (кнопка «Комплект документов при
увольнении») показывает список форм в таблице `НастройкиПечатныхФорм`,
а сами формы лежат на страницах `ПечатнаяФорма1` … `ПечатнаяФорма14`.
Доступна из них **только та, чья строка сейчас текущая**: попытка
сохранить `ПечатнаяФорма2`, пока выбрана первая строка, падает с

```
Элемента формы с именем <ПечатнаяФорма2> не найдено.
```

**Порядок:** `activate_header_element("НастройкиПечатныхФорм")`, затем
`navigate_next_row` до нужной строки, `get_selected_rows` — убедиться,
что это та форма, — и только потом `save_table_document_to_file` по
соответствующему номеру. Нумерация страниц совпадает с порядком строк
в таблице, но проверять всё равно нужно: часть форм в комплекте
недоступна (их поле имеет `Видимость:Нет`), потому что данные берутся
из отдельных документов, которых в базе нет.

В том же подменю печати оказалось **три кнопки с заголовком «Комплект
документов при увольнении»** (`ПодменюПечатьОбычное__1`, `__2`, `__3`) —
видима и работает только третья. Ещё один случай к разделу про
одинаковые заголовки.

## Отчёт «Настройки организации» показывает даты выплаты, которых нет

Вопрос «когда выплачивается аванс и зарплата» естественно проверять
отчётом `Отчет.НастройкиПрограммыЗарплатаКадры` (кнопка «Настройки
организации» в карточке организации). Он выдаёт:

```
Дата выплаты зарплаты    в начале следующего месяца
Дата выплаты зарплаты    20
Дата выплаты аванса      5
```

Выглядит как настройка базы. **Это не данные.** В регистре сведений
`НастройкиЗарплатаКадрыРасширенная`, откуда отчёт берёт эти показатели,
у всех трёх организаций демо-базы:

```
ДатаВыплатыАвансаНеПозжеЧем           0
ДатаВыплатыЗарплатыНеПозжеЧем         0
ВыплачиватьЗарплатуВПоследнийДеньМесяца  Нет
```

то есть срок не задан вообще. Числа в отчёте — значения по умолчанию,
зашитые в его модуль (`Reports/НастройкиПрограммыЗарплатаКадры/Ext/
ManagerModule.bsl`, вызовы `ДобавитьПоказатель`): для зарплаты там `"5"`,
для аванса `"20"`. В печатной форме они к тому же выводятся напротив
противоположных подписей — зарплата 20, аванс 5.

**Как проверять правильно.** Открыть список регистра
`e1cib/list/РегистрСведений.НастройкиЗарплатаКадрыРасширенная` и прочитать
значения; для одной организации — `select_row` по строке открывает форму
записи с полями `ДатаВыплатыАвансаНеПозжеЧем`,
`ДатаВыплатыЗарплатыНеПозжеЧем`, `ВыплачиватьЗарплатуВПоследнийДеньМесяца`.
Пустая ячейка в списке означает ноль, а не «не показано».

Похожий на вид регистр `НастройкиЗарплатаКадры` (без «Расширенная») в этой
базе **пуст полностью** — по имени легко взять не тот.

**Дополнение 01.09.2026.** Нули в регистре — состояние на 30.08.2026;
в тот же день агент по просьбе человека проставил сроки, и сейчас там
у всех трёх организаций аванс `20`, зарплата `5`,
«выплачивать в последний день месяца» = Нет. Сама ловушка не устарела:
отчёт по-прежнему выводит те же числа независимо от регистра, поэтому
совпадение отчёта с данными сейчас — случайность, а не признак того,
что отчёту можно верить.

Отдельно стоит сверять настройку с фактом: даты в проведённых ведомостях
(`СпособВыплаты` = «Аванс» / «Зарплата за месяц») показывают, как платят
на самом деле, и с настройкой могут не совпадать.

## Отправленное письмо возвращается из IMAP новым документом

Исходящие письма, помеченные на удаление и снесённые обработкой
«Удаление помеченных объектов», после проверки списка **оказались
на месте** — с другими ссылками, другими номерами и датами, равными
времени фактической отправки (11:37, 17:12, 17:57, 17:58).

Это не сбой удаления. Команда «Отправить и получить» не только
отправляет письмо, но и **синхронизирует папку «Отправленные»
на сервере**: копия ушедшего письма приходит обратно по IMAP и
создаёт НОВЫЙ документ `ЭлектронноеПисьмоИсходящее`. Тот, что был
создан кнопкой «Ответить», и тот, что пришёл с сервера, — два разных
объекта с одинаковой темой.

За день их получилось вдвое больше, чем создавал агент: четыре «своих»
и четыре «вернувшихся».

**Правило:** удалил исходящее письмо — перечитай список
`get_table_data(object_type=2, object_name="ЭлектронноеПисьмоИсходящее")`
и убедись, что нет копии с тем же текстом и другой ссылкой.
То же касается любой проверки «письмо ушло»: документов на одно
отправленное письмо может быть два.

## Приём на работу молча пишет в регистры охраны труда

Физлицо принятого сотрудника не удаляется даже после удаления самого
документа приёма. Обработка удаления называет причины по одной,
и их оказалось три:

```
РегистрСведений.БудущиеСобытияМедицинскиеОсмотры
РегистрСведений.ОбновлениеВыдачСИЗ
РегистрСведений.ОбновлениеПериодическихМедицинскихОсмотров
```

Это независимые регистры сведений: документ их заполняет при
проведении, но при отмене проведения и удалении **не чистит**.
В «местах использования» (`МестаИспользованияНеудаленных`) они
не показываются — таблица остаётся пустой.

**Как найти:** в форме результата обработки выбрать объект в таблице
`НеУдаленные` (сначала `activate_header_element`, иначе кнопка
недоступна) и нажать `УстановитьУдалить` — модальный диалог назовёт
одну мешающую ссылку. Убрать её и повторить, пока не кончатся.

**Как убрать:** `e1cib/list/РегистрСведений.<Имя>`, найти строку своего
физлица, `ФормаУдалить`. Колонка «Физ. лицо» имеет имя `Физлицо`,
но заголовок с точкой и пробелом, поэтому `navigate_to_row` по ней
не работает — строку приходится искать перебором `navigate_next_row`.

Подробный разбор — `drafts/словари/УдалениеОбъектов.feature`.

## `check_syntax` отдаёт разбор ПРОШЛОГО файла, если файл не открыть заново

Проверено 02.09.2026 на сводной проверке всех шагов проекта. Свежесобранный
файл проверился с вердиктом «проблем нет», хотя в нём лежало 566
несуществующих шагов. Тот же файл после `open_feature_file` дал честные
566 ошибок. И наоборот: после исправлений `check_syntax` ещё раз выдал
старый список — до тех пор, пока файл снова не открыли в редакторе.

Правило: **всегда два вызова подряд** —

```
open_feature_file(filePath="<полный путь>")
check_syntax(filePath="<тот же путь>")
```

Контрольная проверка стоит одного вызова: допишите в конец файла заведомо
несуществующий шаг и убедитесь, что он в отчёте появился. Если «проблем
не найдено» — значит вы читаете кеш, а не свой файл.

## Генераторы словарей выдавали шаги, которых в Vanessa нет

Три формулировки, размноженные скриптами по 117 файлам из 172, —
566 вхождений:

| Было (шага нет) | Стало |
|---|---|
| `И я нажимаю на кнопку с именем 'X' в таблице 'T'` | `И в таблице "T" я нажимаю на кнопку с именем 'X'` |
| `И элемент формы с именем 'X' существует` | `И элемент формы с именем 'X' присутствует на форме` |
| `И я устанавливаю переключатель с именем 'X'` | `И я меняю значение переключателя с именем 'X' на "$$Значение$$"` |

Плюс два десятка одиночных: переход к строке через `'Колонка=Значение'`
вместо таблицы Gherkin, «заканчиваю» вместо «завершаю редактирование
строки», «активизирую колонку» вместо «активизирую поле с именем»,
«элемента справочника» вместо «справочника».

Причина одна: шаги писались по именам действий MCP (`activate_column`,
`start_edit_row`), а не по библиотеке шагов Vanessa. Имена элементов при
этом были настоящие — врала только обёртка вокруг них.

Генераторы исправлены (`сгенерировать-словарь.py`, `сверить-словарь.py`).
Массовая проверка — `drafts/инструменты/собрать-шаги-для-проверки.py`
плюс пара `open_feature_file` + `check_syntax`.
