# Архитектура

## Зачем это

Подключить LLM к базе 1С через MCP можно за десять минут. Дальше вы просите
«закрой месяц в ЗУП» — и модель начинает бродить по подсистемам, тыкать кнопки
и рано или поздно делает что-то не то. Не потому что она глупая, а потому что
у неё нет контекста: она не знает, в каком порядке в вашей базе выполняются
операции, какие поля обязательны и что считается признаком успеха.

Этот контекст не надо выдумывать. Он уже есть — в тестовых сценариях.

**Тестовый сценарий — это эталонное описание бизнес-процесса.** Он писался
человеком, который знает предметную область, он прогонялся сотни раз, он
покрывает граничные случаи. Всё, чего не хватает модели, в нём уже записано.

Поэтому агент не «работает в 1С». Агент **запускает сценарии** и переводит
их результат на человеческий язык.

## Слои

```
┌──────────────────────────────────────────────────────────┐
│ Человек: «сделай 6-НДФЛ по Крон-Ц за 1 полугодие»        │
└───────────────────────────┬──────────────────────────────┘
                            │ естественный язык
┌───────────────────────────▼──────────────────────────────┐
│ Claude Code                                              │
│   CLAUDE.md  — что агенту нельзя делать никогда          │
│   Skill      — что нужно спросить и в каком порядке      │
└───────────────────────────┬──────────────────────────────┘
                            │ tools/call через MCP
┌───────────────────────────▼──────────────────────────────┐
│ MCP-сервер в менеджере тестирования (38 инструментов)    │
└───────────────────────────┬──────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────┐
│ Vanessa Automation                                       │
│   feature-файл — шаги бизнес-процесса                    │
└───────────────────────────┬──────────────────────────────┘
                            │ тестовое API платформы
┌───────────────────────────▼──────────────────────────────┐
│ Клиент тестирования 1С (пользователь «Агент»)            │
└──────────────────────────────────────────────────────────┘
```

## Кто за что отвечает

| Слой | Отвечает за | Не отвечает за |
|---|---|---|
| `CLAUDE.md` | границы: куда агенту нельзя | конкретный бизнес-процесс |
| Skill | входные данные, порядок вызовов, формат ответа | шаги в интерфейсе 1С |
| feature-файл | шаги в интерфейсе 1С, признаки успеха | диалог с человеком |
| MCP | транспорт | смысл |

Разделение важное. Меняется форма в 1С — правим feature-файл, скилл не трогаем.
Меняется регламент общения с пользователем — правим скилл, сценарий не трогаем.

## Контракт результата

Модель не должна догадываться, что произошло в 1С, по скриншоту или по логу.
Сценарий сам сообщает о себе. Каждый этап обёрнут так:

```gherkin
Попытка
    Когда я нажимаю на кнопку с именем 'Заполнить'
    Тогда открылась форма с именем 'ОбщаяФорма.ДлительнаяОперация'
    И я жду закрытия формы с именем "ОбщаяФорма.ДлительнаяОперация" в течение 1800 секунд
    И Я запоминаю значение выражения '{"success":true,"result":"мы заполнили отчет данными"}' в переменную "РезультатВыполненияАгентомШага5"
Исключение
    И Я запоминаю значение выражения '{"success":false,"result":"возникла ошибка при заполнении отчета"}' в переменную "РезультатВыполненияАгентомШага5"
    Затем я останавливаю выполнение сценариев данной фичи
```

Что это даёт:

- **Сценарий падает управляемо.** Ошибка на шаге 5 не тащит за собой шаги 6–9.
- **Агент читает структуру, а не текст.** JSON парсится однозначно.
- **`result` написан для человека.** Агенту не нужно ничего сочинять —
  он передаёт готовую формулировку.
- **Видно, где именно встало.** Номер переменной = номер этапа.

Читаем результаты **от старшего номера к младшему** и берём первый непустой:
это и есть последний выполнившийся этап.

## Почему переменные глобальные

Vanessa удаляет локальные переменные перед стартом сценария. Агент
устанавливает переменные до запуска, значит они обязаны быть глобальными
(`is_global: true`). Обратная сторона — они живут, пока живёт Vanessa, поэтому
переменные результата надо чистить перед каждым прогоном, иначе прочитаете
итог предыдущего запуска.

## Программная автоматизация, человек и агент

| | Программная автоматизация (обработка, API) | Человек | Агент на сценариях |
|---|---|---|---|
| Скорость | максимальная | низкая | средняя |
| Стоимость запуска | низкая | высокая | средняя |
| Стоимость изменения | высокая: нужен разработчик | нулевая | низкая: правка сценария |
| Работа через UI | нет, мимо интерфейса | да | да |
| Проверки платформы | обходятся | срабатывают | срабатывают |
| Нестандартная ситуация | падает | сам разберётся | передаёт человеку |
| След в журнале | часто «системный» | пользователь | отдельный пользователь `Агент` |

Главное отличие агента от обработки — он ходит **через интерфейс**, а значит
проходит те же проверки заполнения, те же блокировки и те же права, что и
человек. Ничего не проскочит мимо контроля только потому, что «мы записали
документ программно».
