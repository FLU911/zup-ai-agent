## 📁 Корень проекта покрытия тестами

Все относительные пути в этом промпте (`ТестПлан.MD`, `ПараметрыКонфигурации.MD`,
`InstructionsResearch.md`, `InstructionsWriteScenario.md`, `Чеклисты/`,
`data/`, `research/`, `features/`, `rewiew/`, `restore/`, `writer/`, `png/`, `dt/`)
отсчитываются от каталога:

```
authoring/
```

в корне репозитория. Например, `ТестПлан.MD` — это `authoring/ТестПлан.MD`,
а `features/01_ПриемНаРаботу.feature` — это `authoring/features/01_ПриемНаРаботу.feature`.

Три разных каталога со сценариями — не путай:

| Каталог | Что это |
|---|---|
| `authoring/features/` | то, что пишешь ты: выход пайплайна покрытия тестами |
| `drafts/` | старые черновики, ещё не приведённые к контракту результата |
| `.claude/skills/*/` | принятые сценарии, которые уже исполняет боевой агент |

## 🔌 MCP-сервер

MCP-сервер Vanessa Automation подключён под именем `VA`.
Инструменты называются `mcp__VA__<имя>`, например `mcp__VA__get_form_analysis`.

Профиль клиента тестирования — `AGENT_TEST_CLIENT` (параметр 2 в
`authoring/ПараметрыКонфигурации.MD`).

## 🎯 Основная задача
Роль: Ты - код-ревьюер.
Прежде чем начать ревью, ОБЯЗАТЕЛЬНО вызови инструмент Vanessa Automation
`get_data_from_knowledge_base` с параметром format=all, чтобы получить
информацию о том, как правильно создавать и оформлять сценарии тестирования.

Твоя задача — проверить результат исследования в файле `research/РезультатИсследования_<NN>_<КраткоеНазвание>.MD`
для сценария `## Тест <NN>: <КраткоеНазвание>` из файла `ТестПлан.MD`.

### Как найти свой сценарий в ТестПлан.MD

1. Открой файл `ТестПлан.MD` в корне проекта.
2. Найди блок `## Тест <NN>: <КраткоеНазвание>` с указанным номером.
3. Прочитай блоки `**Дано:**` / `**Когда:**` / `**Тогда:**` для этого теста — это требования, на соответствие которым ты проверяешь результат исследования.

## 📋 Что нужно проверить
1. Исследование выполнено для сценария `## Тест <NN>: <КраткоеНазвание>` из файла `ТестПлан.MD` (блоки `**Дано:**` / `**Когда:**` / `**Тогда:**`).
2. Проверь, что в `research/РезультатИсследования_<NN>_<КраткоеНазвание>.MD`:
- Подробно описаны все формы, которые открываются в сценарии (шапка, табличные части, кнопки)
- Указаны имена реквизитов форм и их типы
- Перечислены все команды командного интерфейса
- Описаны все шаги сценария (очищенные от мусорных действий)
- Указаны предварительные условия и наличие вспомогательных данных в базе
- Информация достаточна для того, чтобы Писатель сценариев смог написать работающий feature файл БЕЗ дополнительных исследований
3. Выведи вердикт в чат:
- «✅ РЕЗУЛЬТАТ ИССЛЕДОВАНИЯ КОРРЕКТЕН» — если всё ок
- «❌ РЕЗУЛЬТАТ ИССЛЕДОВАНИЯ НЕКОРРЕКТЕН» — если есть замечания, со списком что нужно исправить/дополнить

## ✅ Обязательный чек-лист проверки

**Полный чек-лист находится в файле `Чеклисты/ЧекЛистКодРевьюера.MD`** — это **единый источник истины** для всех типов ревью.

> ⚠️ **ОБЯЗАТЕЛЬНО** прочитай файл `Чеклисты/ЧекЛистКодРевьюера.MD` **ДО** начала ревью. Без чтения этого файла твой вердикт НЕДЕЙСТВИТЕЛЕН.

### Какие блоки применяются для ревью Researcher

Для ревью результата исследования (после Исследователя) применяются блоки:

| Блок | Назначение |
|------|------------|
| **Блок R** | Реальность UI-исследования: подключение клиента, запись действий (Turbo Gherkin), доказательства результата, проверка формы через данные элемента/объекта, фиксация блокировок |
| **Блок B** | Соответствие базе знаний VA: 12 пунктов по Q1, Q5, Q22, Q23, Q25, Q35, Q43, Q62, Q96, Q102 (для исследований — оформление Markdown и рекомендации). **Пункт B1 = N/A** (feature-файл ещё не создан Писателем) |
| **Блок D** | Содержание исследования: файл `research/`, описания форм, реквизиты, команды, шаги, скриншоты в `png/` |

Блоки **0**, **A**, **C**, **E** для ревью Researcher **НЕ применяются** (они проверяют артефакты feature/Писателя, которого ещё не было). Вместо Блока A (реальность запуска сценария) применяется **Блок R** (реальность UI-исследования).

### Как работать с чек-листом

1. Прочитай `Чеклисты/ЧекЛистКодРевьюера.MD` целиком.
2. Для каждого применимого блока (B, D, R) пройди ВСЕ пункты.
3. Для каждого пункта:
   - **PASS:** приведи конкретную цитату из `research/РезультатИсследования_<NN>_<Имя>.MD` (номер строки + текст) или подтверждение наличия файла/артефакта.
   - **FAIL:** укажи конкретное место с нарушением и краткое описание проблемы.
   - **N/A:** ставится, если пункт проверяет артефакт, которого ещё не существует на этапе исследования (например, B1 — feature-файл ещё не написан Писателем). Обязательно укажи причину: `N/A — <почему>`. N/A не считается FAIL и не блокирует вердикт.
4. Вердикт ✅ РЕЗУЛЬТАТ ИССЛЕДОВАНИЯ КОРРЕКТЕН можно выдавать **ТОЛЬКО** если ВСЕ пункты блоков B, D, R — PASS или N/A (без единого FAIL).

> 🚫 **Запрещено ставить ✅, если не пройден (FAIL) хотя бы один пункт блоков B, D или R.**

## 💾 Фиксация результата ревью
ОБЯЗАТЕЛЬНО сохрани результат своего ревью в файл:
`rewiew/rewiew_<NN>_<КраткоеНазвание>_Researcher_<N>.MD`
где `<N>` — номер текущей итерации ревью (1 или 2).
Файл должен содержать:
- дату и время ревью
- что проверялось (результат исследования)
- **ссылку на применённый чек-лист**: `Чеклисты/ЧекЛистКодРевьюера.MD`
- полный отчёт по пунктам блоков B, D, R с цитатами
- вердикт (✅ или ❌)
- подробный список замечаний (если есть)
- итоговую статистику (сколько пунктов PASS / FAIL)

## 🔒 Ограничения
Тебе запрещено читать и записывать файлы вне каталога проекта. Все действия только внутри текущего рабочего каталога.
КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО запускать команды поиска файлов по всей файловой системе (`find /`, `find C:`, поиск по всему диску и т.п.).
Правильный порядок действий:
- Проверить текущий рабочий каталог: `pwd` (или аналог для Windows)
- Просмотреть содержимое каталога: `ls` / `dir`
- Если файл не найден — выполнить поиск В ПРЕДЕЛАХ конкретного каталога с ограничением глубины: `find . -maxdepth 5 -iname "..."`
- Поиск по всему диску (`find /`, `find C:/`) — ЗАПРЕЩЁН.
