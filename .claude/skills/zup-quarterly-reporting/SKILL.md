# Квартальная отчётность

Написан 30.08.2026 после ночи, ушедшей на одно контрольное соотношение.
Существующий скилл `zup-6ndfl-report` — старого образца: он запускает
готовый сценарий целиком. Этот описывает работу в словарной архитектуре
и покрывает все три отчёта, а не один.

## Что надо сделать ДО того, как создавать отчёт

Половина ошибок выгрузки лечится не в отчёте, а в справочниках.
**Титульный лист заполняется только в момент СОЗДАНИЯ отчёта** —
кнопка «Заполнить» его больше не трогает. Значит, ошибку в реквизитах
организации нельзя исправить «на лету»: отчёт придётся создавать заново.

| Что | Где | Без чего не пройдёт |
|---|---|---|
| Код по ОКТМО | `Справочник.РегистрацииВНалоговомОргане` | 6-НДФЛ, персонифицированные |
| ИНН организации ровно 10 цифр | `Справочник.Организации` | 6-НДФЛ |
| ОГРН, регистрационный номер СФР | `Справочник.Организации` | ЕФС-1 |
| Ответственные лица (руководитель) | регистр ответственных лиц | все три |
| ИНН физлиц без префиксов 00, 96, 98 | `Справочник.ФизическиеЛица` | персонифицированные |

**Подписант ЕФС-1 должен быть сотрудником ТОЙ ЖЕ организации**, иначе
не находится его должность и выгрузка падает. У филиала это отдельный
человек, не генеральный директор головной.

**ИНН филиала правится хитростью:** поле на форме организации-филиала
только для просмотра. Снять флаг «Это — филиал» — поле станет
доступным; поставить обратно — ИНН подтянется от головной.

## Порядок

```
1. e1cib/app/Отчет.РегламентированныйОтчет6_НДФЛ   ← с ПОДЧЁРКИВАНИЕМ
2. set_value 'Организация' <орг> exact_match:true
3. click_button 'УстановитьПредыдущийПериод'       ← столько раз, сколько надо
4. get_form_element_data 'ПолеВыбораПериодичностиПоказаПериода'  ← ПРОВЕРИТЬ
5. click_button 'ОткрытьФормуОтчета'               ← создаёт НОВЫЙ отчёт
6. click_button 'Заполнить'
7. click_button 'Сохранить'                        ← ОТДЕЛЬНЫМ вызовом
8. click_button 'Проверить'                        ← контрольные соотношения
9. click_button 'ПроверитьВыгрузку'
```

Три отчёта, три объекта:

| Отчёт | Объект метаданных | Период | Кнопка КС |
|---|---|---|---|
| 6-НДФЛ (с 2021 года) | `РегламентированныйОтчет6_НДФЛ` | квартал | есть |
| ЕФС-1 (ОСС, травматизм) | `РегламентированныйОтчетЕФС1ОСС` | квартал | **нет** |
| Персонифицированные сведения | `РегламентированныйОтчетПерсонифицированныеСведенияОФизическихЛицах` | **месяц** | **нет** |

Сохранённые отчёты потом лежат в `Документ.РегламентированныйОтчет`,
а не в справочнике. Открывать по навигационной ссылке из
`get_table_data(object_type=2, object_name="РегламентированныйОтчет")`.

## Как читать результат проверки

- **Контрольные соотношения.** Если нарушений нет — только модальный
  диалог. Если есть — открывается окно «Проверка контрольных
  соотношений», табличный документ в нём называется `Результат`.
  Окно **не обновляется и само не закрывается**: перед каждой проверкой
  закрывать его, а признаком чистоты считать его отсутствие в
  `get_window_list_testclient`.
- **Выгрузка.** Всегда модальный диалог; при ошибках открывается окно
  «Навигация по ошибкам» с таблицей `ТаблицаСообщений`.

Разбирать результат удобнее выгрузкой:
`save_table_document_to_file('Результат', format='xlsx')` и
`python инструменты/xlsx2tsv.py`.

## Когда контрольное соотношение не сходится

**Не подбирать.** Полная методика с каталогом ошибок, таблицей
рычагов «что на что влияет» и разбором реального случая —
`docs/08-разбор-ошибок-отчетности.md`. Общий алгоритм чтения базы —
`docs/07-как-читать-базу.md`.

Коротко про 6-НДФЛ, Раздел 2:

| Строка | Откуда | По какому признаку отбирается |
|---|---|---|
| 120, 130 доход и вычеты | регистр «Учет доходов для исчисления НДФЛ» | месяц налогового периода |
| 140 исчислено | «Расчеты налогоплательщиков…», Приход | **дата получения дохода** |
| 160 удержано | «Расчеты налогоплательщиков…», Расход | **период движения** |
| 170 не удержано | то же, Σ положительных сальдо по аналитике | |
| 180, 190 | излишне удержано и возвращено | |
| Раздел 1 | «Расчеты налоговых агентов с бюджетом по НДФЛ» | срок перечисления |

Из-за разных признаков отбора у 140 и 160 доходы без денежной выплаты
(подарки, натуральный доход) легко разъезжаются по кварталам. Первое,
что проверять при разрыве, — реквизит `ДатаПолученияДохода` у таких
документов: он должен лежать в том же квартале, что и дата документа.

Что чем лечится:

| Нарушение | Рычаг |
|---|---|
| КС 1.11 (140 ≠ 13 % базы) | «Операция учета НДФЛ», закладка «Исчислено по 13 %». Двигает 140 и 170 одинаково, на КС 1.14 не влияет |
| КС 1.14 (140 < 160 + 170 − 180 − 190) | привести в порядок даты получения дохода и **перезаполнить ведомости**, которыми налог удержан |
| КС 1.45 (Раздел 1 против Раздела 2) | Раздел 1 берётся из другого регистра — правка только «налогоплательщиков» его ломает |

Не работает никогда: возврат НДФЛ (180 и 190 перетекают друг в друга),
«передано на взыскание» (в 6-НДФЛ не попадает вовсе), прямая правка
регистра «Переносом данных» без правки документа-источника.

## Дата подписи

Это ЯЧЕЙКА табличного документа, а не поле формы. Ячейки титульного
листа именованные: `ДатаПодписи`, `ОргПодписант`. Правятся только
сценарием Vanessa, шаг называется «в табличн**ый** документ … я ввожу
текст» (поиск по «в табличном документе» его не находит).

Три условия запуска: строка `Контекст: Дано Я запускаю сценарий
открытия TestClient или подключаю уже существующий`; отчёт открывается
ВНУТРИ сценария («Я открываю навигационную ссылку»), потому что
`run_scenario` закрывает все окна на старте; после упавшего прогона —
режим `reloadAndRun`.

На суммы 6-НДФЛ смена даты подписи не влияет (проверено на всех девяти
отчётах 29.08.2026).

## Что нельзя

- **Пометить регламентированный отчёт на удаление через MCP** — кнопки
  нет ни в форме отчёта, ни в журнале. Каждое нажатие
  `ОткрытьФормуОтчета` создаёт НОВЫЙ отчёт, дубли накапливаются.
  Создавать отчёт заново только тогда, когда это действительно нужно.
